4. VAL 缓存读取时逐条核对规范化计划与 inference，覆盖新评测及 resume，

5. 删除 59 条非法 `on agent` 边，保留物品合法支撑及房间归属；

   修正其中 56 个冲突。房间边不产生第二条独立 `agent_at`；

6. 灯具 `light_on` 的对象参数扩展为 `physobj`，`is_light_on` 同步扩展，

   不将先前提出的通电／点亮双状态同步视作已批准方案。

仍在讨论的设计建议：

- 空间无环性：Python 验证输入 scene；PDDL 的放置前置条件表达后代禁放，
  让规划器与原生 VAL 使用同一规则；Python 回放／导出补充同语义不变量检查。
  传递关系可以采用派生谓词，但尚未完成本工具链兼容验证，未确定最终实现。
- 灯具状态简化：用户提出仅保留 light_on，当前建议对纯照明灯具只保留
  `can_be_lighted` / `is_light_on`，删除这类节点的 `is_powerable` / `is_powered_on`，
  将初始已通电的照明语义核对后迁移为已点亮，参考计划对应改用 light_on。
  domain 的 power_on/off 仍供咖啡机、水壶等设备使用，不全局删除。
  为保留关闭照明能力，建议补充 light_off；核对兼有其他功能的光源，
  不依据家具类别或名称字符串批量删除通电能力。该简化方案仍处于讨论阶段。
- 防环的 PDDL 变化：拟增加 on/in 传递关系的派生谓词及对应 requirements，
  在四个普通／相邻放置动作中加入“目标不是被放置物的后代”的否定前置条件。
  保留对象不等约束，派生关系不写入 scene/init，也不由动作效果手工维护。
  房间作为空间根节点的约束及家具／设备移动关系还需一起核查，
  不将 on/in 防环等同于所有空间不变量均已解决。两个 domain、生成脚本、
  指纹及解析／回放／规划器兼容检查均需同步；尚未实施或验证派生谓词方案。

进一步只读核查发现：59 条非法边删除后，59 个物品仍各自有唯一房间路径，
机器人 `agent.location` 也都能解析到同一房间；59 个场景已有机器人房间边，
其中仅 3 个一致，**56 个与 `agent.location` 推导结果冲突**。
因此无需为这些物品任意另找房间；应保留合法位置，并以当前 PDDL 实际采用的

## 1. 多物交付在 scene 回放中丢失：14 道参考任务

PDDL 的 `hand_over_to_person` 累积 `p_holding(person, object)`，
但 `SceneGraphManager._apply_effect` 将 `person.p_holding` 写成单个字符串，
第二次交付覆盖第一次；初态提取也仅支持一个字符串。

全部参考计划回放后，14 道的 scene→PDDL 末态与直接 PDDL 末态不同，
共丢失 22 条 `p_holding`，其余 275 道末态一致；没有回放异常。
例如故事书和小夜灯任务 `eb91424f-f1cb-4d9c-91bf-c2f319fe9c84`，
scene 最后只保留小夜灯，直接 PDDL 仍保留两件交付物。

影响 scene 回放、导出及依赖 scene 的闭环算法。正式 D1 当前直接执行 PDDL
回放，不经过这个单字符串字段，因此不能将其报告为 D1 已丢失交付物。

建议让人的持有字段支持多物集合，并同步初态提取、动作效果、邻接验证和
场景摘要，兼容旧字符串。不要通过禁止多物交付来改写任务要求。

## 2. 操作不检查外层关闭容器：已有 2 道咖啡参考任务受影响

`pick_from_receptacle` 仅检查直接容器打开；`pick_from_surface`、`pour_into`
等没有检查目标的外层容器。`navigate` 也不提供该约束。

原生 VAL 接受了以下不合理计划，且明确验证了对应错误结果：

- 普通／液体 domain：从关闭柜子内部的开放盒子里拿出苹果，柜门始终关闭。
- 液体 domain：向关闭柜子内部的杯子倒水，柜门始终关闭。

现有参考计划中，以下两道咖啡机均以 `in` 位于可打开但未打开的厨岛柜里，
计划未打开厨岛柜就加水、装料、开机、出杯和取杯；两条原计划均经 VAL 判 valid：

| ID | 原指令 |
| --- | --- |
| `f8e914bb-3f3a-43de-8b8f-c86cbaf6894f` | Could you make a coffee and bring it to my friend in the game room? |
| `2cd06e0a-88a9-45a6-a5e3-a378199d6414` | Go to the kitchen, use the coffee machine to brew a cup of coffee into a mug, and place the mug on the kitchen island. |

自动扫描仅覆盖两种 pick 和 pour_into，检出 2 道／4 个步骤；不是所有操作的影响上限。
建议先核对咖啡机应当是 `on` 台面还是 `in` 柜内，再修 scene 或补前序开门步骤。
domain 应统一表达操作目标可访问性，检查沿 on/in 路径经过的关闭内部空间；
不要把“放在关闭柜子的顶面”也误判成不可访问。

## 3. 容器可以放进自己的后代：两个 domain 均已复现

初态小盒子在大盒子内，大盒子在桌上。执行：

```lisp
(pick_from_surface agent_0 big_box table_1)
(navigate agent_0 big_box small_box)
(place_in_receptacle agent_0 big_box small_box)
```

VAL 判合法，并同时满足 `small_box in big_box` 和 `big_box in small_box`。
`place_in_receptacle` 只有对象不等约束，没有祖先／后代约束。
这是最小反例证明的 domain 漏洞，本轮没有证明现有参考计划产生了这样的环。

建议将空间无环性作为共享不变量，覆盖普通及相邻摆放、on/in 混合路径和初态校验。
不能仅增加直接互相包含检查，否则更长的环仍可能通过。

## 4. VAL 缓存中的 plan 没有与 inference 对照

`run_judge_stage` 验证输入来源元信息、domain 指纹和初态文本 hash，
但实际评审使用 `validation["plan"]`，没有将其与对应 inference 的规范化计划比较。

隔离复现：先对合法 pick 计划运行真实 VAL，然后只修改临时 VAL 结果 case 中的
plan，替换为未持有杯子就 place 的计划，保留原输入和元信息。
替换计划单独运行 VAL 为 invalid，但 judge 阶段仍接受它并发出四个维度请求。

此处使用 FakeClient，无真实模型调用；证明的是缓存错配未被拒绝，
不能据此声称真实裁判一定给高分或已有历史实验被污染。

建议在新评测及 resume 路径都核对 case 的规范化计划与推理输入，
并绑定上游实际结果内容；仅校验 provenance 元信息不足以发现这种错配。

## 5. 灯具能力、类型与结果状态不统一

76 个场景中共 880 次家具节点声明了 `can_be_lighted`，
但 `light_on` 参数与 `is_light_on` 仅接受小物品 `object` 类型。
以 furniture 灯具调用 light_on，两个 domain 均被类型检查判 invalid。

其中 2 条参考计划实际操作这类家具灯：
`7de7655d-b0c6-40e9-b578-70914cdae455`（客厅吸顶灯）、
`e813354b-12a3-4190-bb1e-fd4910f0b601`（落地灯）。
参考计划使用 `power_on`，只得到 `is_powered_on`。
不能把 76 个场景都算成失败任务，也不能认为这两条 power_on 参考必然不完成指令；
问题是声明可点亮，却无法用点亮动作操作，且同类意图的末态表达不一致。

建议明确电灯与蜡烛等对象的状态语义，再统一动作参数类型和 D1 判定口径。
避免把所有设备通电都等同于发光。

## 6. 原始 scene 与 PDDL / D2 输入仍有数据差异

- 5 道场景含非法 PDDL 标识符，如 `children's_toys_63`、`stuffed toy_22`、
  `under‑stair_storage_unit_22`、`t‑shirt_57`。初态转换过滤了有关事实及非法名称对象；
  算法看到的 scene 和可规划对象集合因此不同。目前未证明这些对象是参考计划必须操作的对象。
- 59 道原始场景有家具／物品 `on agent` 一类关系，例如桌子在机器人上。
  PDDL 提取会忽略它们，但 D2 场景摘要仍呈现这类关系。
  这不是 59 道 PDDL 末态多位置错误，更像旧位置编码／方向约定未统一。

建议对非法名称建立确定性的重命名映射，联动更新指令中的显式名称、links、
agent/person 字段、计划和目标。旧机器人位置关系应核对 `agent.location`
后规范化；输入端统一验证，避免各阶段选择性忽略。

## 优先级与边界

优先修复实际影响参考数据的多物交付回放和两道关闭柜内咖啡机任务，
并补上评测缓存计划绑定；随后统一可访问性、空间无环性及 scene 数据规范，
最后统一灯具状态语义。

上一轮移动位置唯一性与单物体容量问题不在本轮新增问题中。
未重跑外部算法或真实 LLM 评分，不能量化这些问题对算法排名的影响。
液体容量、混合、冷却、精确饮用温度和主观舒适度仍是已声明的建模边界；
已隔离的 7 道任务不在当前正式集合及上述计数中。
